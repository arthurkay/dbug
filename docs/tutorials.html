Request Builder

Send HTTP requests with full control over every detail — method, URL, headers, body, query params, and authentication.

1 Choose a Method

Click the method dropdown (left of the URL bar) and select GET, POST, PUT, PATCH, DELETE, HEAD, or OPTIONS. The method color updates automatically.

2 Enter the URL

Type the full URL or just the path if you have a base URL set. Use {{variable}} syntax for dynamic values — they'll be substituted from your active environment at send time.

3 Configure the Request

Use the tabs below the URL bar to set up your request:

TabWhat to configure
ParamsQuery parameters as key-value pairs (appended to URL)
HeadersRequest headers (Content-Type, Accept, custom headers)
BodyRequest body — choose JSON, Form Data, or Raw text
AuthAuthentication — Bearer token, Basic credentials, or API Key

4 Send and Inspect

Click Send (or press the button). The response appears in the bottom pane with status code, timing, and a syntax-highlighted body. Select any text in the response to copy it.

Tip: Your last request is automatically saved. When you reopen dbug, everything is restored — method, URL, headers, body, and even the last response.

Collections

Organize your requests into collections — groups of related endpoints for an API or project.

1 Create a Collection

Go to the Collections screen from the sidebar. Click New Collection, give it a name (e.g., "User API", "Payment Service"), and save.

2 Add Requests

Open the Request Builder, configure your request, then click Save. Choose the collection to save it into. The request appears in the collection's list.

3 Set Global Headers

Each collection can have global headers that apply to all requests in that collection. Click the collection header to expand it, then add headers in the "Global Headers" section. These are merged with per-request headers at send time.

4 Set Collection Auth

Configure authentication at the collection level — all requests inherit it automatically. Supports Bearer, Basic, and API Key. Individual requests can override with their own auth if needed.

5 Switch Between Endpoints

When a request is open in the builder, the collection sidebar shows all sibling requests. Click any to switch instantly — the builder loads the latest history for that endpoint.

Tip: Collections can be exported as JSON files and shared with your team. Use the export/import buttons in the Collections screen.

Environments

Define variables per environment and switch between them without changing your requests.

1 Create an Environment

Go to the Environments screen from the sidebar. Click New Environment and name it (e.g., "Development", "Production", "Staging").

2 Add Variables

Inside the environment, add key-value pairs. Common variables include:

KeyExample Value
base_urlhttp://localhost:3001
api_keysk_live_abc123
tokeneyJhbGciOiJIUzI1NiJ9...
host_idhost-001

3 Activate an Environment

In the sidebar, click the environment selector and choose which environment to use. Only one environment is active at a time. The selector is available on every screen.

4 Use Variables in Requests

Reference variables with double curly braces: {{base_url}}, {{api_key}}, {{token}}. They work in URLs, headers, body, and query params. Variables are resolved at send time.

Tip: Variables imported from OpenAPI specs (like path parameters {id}) are automatically converted to {{id}} syntax and appear as user-editable environment variables.

Authentication

Three authentication methods built in — configure per-request or at the collection level.

1 Bearer Token

Select Bearer in the Auth tab. Paste your JWT or API token. It's sent as Authorization: Bearer <token> in the request header.

2 Basic Auth

Select Basic in the Auth tab. Enter username and password. They're Base64-encoded and sent as Authorization: Basic <credentials>.

3 API Key

Select API Key in the Auth tab. Enter the key name and value. Choose where to send it — as a Header (e.g., X-API-Key: abc123) or as a Query Parameter (e.g., ?api_key=abc123).

Tip: Collection-level auth is inherited by all requests. If a request has its own auth configured, that takes precedence over the collection's auth.

History

Every request you send is automatically logged with full details — URL, headers, body, response, timing, and status code.

1 Browse History

Go to the History screen from the sidebar. Entries are listed newest first. Each shows the method, URL, status code, and response time at a glance.

2 Search and Filter

Use the search bar to filter by URL, method, or status code. Type a method name (GET, POST) or a status code (200, 404) to narrow results.

3 Revisit a Request

Tap any history entry to load it back into the Request Builder with all its original details — URL, method, headers, body, params, and the response it got. This is useful for re-running or tweaking past requests.

4 History-Aware Endpoints

When you open an endpoint from a collection, dbug automatically loads the most recent history for that request. The URL, headers, body, and params reflect your last execution — not just the saved template.

Tip: History is stored locally in SQLite. Use the trash icon to delete individual entries, or clear all history from the History screen.

Mock Server

Built-in mock server on port 3001. Define endpoints with custom responses, status codes, headers, and delays.

1 Start the Mock Server

Go to the Mock Server screen from the sidebar. Toggle the server on. It starts listening on http://localhost:3001.

2 Add an Endpoint

Click Add Endpoint. Set the HTTP method, path (e.g., /api/users), status code, response body (JSON), and optional delay in milliseconds.

3 Test Your Endpoint

Send a request to http://localhost:3001/api/users from the Request Builder (or any HTTP client). The mock server returns your defined response.

4 Use Delays for Realism

Set a delay (e.g., 500ms) on an endpoint to simulate network latency. Useful for testing loading states and timeouts in your frontend.

Tip: Mock endpoints can use environment variables in their response bodies with {{variable}} syntax, just like the Request Builder.

OpenAPI Specs

Import OpenAPI 3.x specifications and browse endpoints with full parameter details, request body schemas, and response structures.

1 Import a Spec

Go to the OpenAPI Specs screen. Click Import and choose a source:

SourceHow
FileSelect a local .json or .yaml OpenAPI spec file
URLPaste a URL to a hosted spec (e.g., https://api.example.com/openapi.json)

2 Browse Endpoints

After import, all endpoints are listed grouped by tag. Each shows the method, path, operation name, and parameter counts. Click an endpoint to see its full details.

3 API Mode vs Docs Mode

Toggle between two views:

ModeWhat it shows
APIInteractive — parameters, JSON schema preview, send requests directly
DocsDocumentation — description, parameter table, request body schema, response schemas

4 Send from Spec

In API mode, click Send on any endpoint to load it into the Request Builder with the correct method, URL, and path parameters pre-filled. Fill in the values and send.

Tip: Path parameters like {id} in the spec are automatically converted to environment variables ({{id}}) that you can set per environment.

Variables

Dynamic values that are resolved at send time — keep your requests clean and environment-aware.

1 Syntax

Use double curly braces around a variable name: {{variable_name}}. Spaces and underscores work inside the name.

2 Where Variables Work

Variables can be used in:

LocationExample
URL{{base_url}}/api/users
HeadersAuthorization: Bearer {{token}}
Body{"key": "{{api_key}}"}
Query Params?token={{api_key}}

3 Variable Sources

Variables come from two places:

SourceDescription
EnvironmentDefined in the Environments screen, selected in the sidebar
OpenAPI ImportPath parameters from imported specs become editable variables

Tip: The URL bar in the Request Builder has a hover tooltip that shows the resolved URL with all variables substituted, so you can preview the final URL before sending.

Settings

Customize dbug's appearance and behavior to match your workflow.

1 Syntax Highlighting Theme

In Settings, choose from 6 syntax themes for the response body viewer:

ThemeStyle
DefaultBalanced contrast, easy on the eyes
GitHubClean, familiar to GitHub users
MonokaiVibrant, high contrast
DraculaPurple-tinted, dark-friendly
OneDarkVS Code-inspired, muted tones
SolarizedWarm, carefully calibrated colors

2 Theme Mode

Toggle between dark and light mode using the theme button in the nav bar. Your preference is saved across sessions.

3 Window Persistence

dbug remembers your window size, position, and maximized state. When you reopen, everything is restored to where you left it.

Tip: The response body text is fully selectable. Use the theme toggle in the nav bar to switch modes, and try different syntax themes to find what's most readable for you.
